Executive summary

BodhAssess processes sensitive personal data — name, email, date of birth, phone, gender, employer code and psychometric responses — for identified individuals, on behalf of client organizations.

3Critical
4High
5Medium
2Low

The platform has no enforced authentication in either deployment profile, and its sole credential is a date of birth that is itself stored as a visible data field.

Together those two facts mean the entire respondent database is reachable, and every account impersonable, by anyone who can reach the API. Everything else in this report is secondary to them.

The engineering quality of this codebase is high in the places that matter. Schema changes are disciplined (Flyway with ddl-auto: validate), the activity trail is thoughtfully designed, rich-text input is rejected rather than sanitized, and the container port policy is a real control born of a real incident. Those are genuine assets and an auditor will credit them — §5 lists them in full.

Applicability

Not all nine frameworks bind BodhAssess. Stating this precisely matters — scoping a programme against frameworks you are not subject to wastes money and dilutes the ones that do apply.

Findings

Fourteen findings, ordered by severity. Each carries the evidence it rests on, the impact, and the fix. Findings marked verify need confirmation on the production host before being treated as confirmed or dismissed.

Critical — 3 findings
C-1

Authentication is not enforced in any environment, including production

Evidence
  • application.yml — app.security.require-auth: ${REQUIRE_AUTH:false} in both the development and production profiles.
  • security/ActorFilter.java — with the flag off the filter resolves the bearer token for logging and serves the request either way. Nothing is rejected.
  • docker-compose.yml — the api service passes only the profile and DB credentials. REQUIRE_AUTH is not set.
  • RegistrationTokenController.java:57 — states it in a code comment: "nothing in this project has an auth filter yet, so the admin endpoints here are as open as the public one."
Impact

Every endpoint except Data Studio (which enforces its own check) is reachable without credentials:

  • GET /api/reports/getRespondents — paged name, email, organization and attempt status for every respondent in the platform, with a search parameter.
  • GET /api/reports/getRespondentDetail/{id} — full profile plus every assessment allotted.
  • POST|PUT|DELETE /api/respondents/* — create, modify and delete people.
  • POST /api/registration-tokens/create — mint registration links that create accounts.
  • All questionnaire, question, assessment, organization and practitioner CRUD.

A complete failure of access control. Under DPDP this is a failure of reasonable security safeguards (§8(5)), and any exploitation is a reportable personal data breach.

Unverified — check before acting

secrets.env is gitignored and not in the repository. It is possible — not likely, given the comment above and the variable's absence from compose — that this is set on the droplet.

# on the production droplet
docker exec bodhpsychometric-api env | grep -E 'REQUIRE_AUTH|JWT_SECRET'

# from anywhere — if this returns data, the API is open
curl -s https://api.bodh.biz/api/reports/getRespondents | head -c 300
Fix

Set REQUIRE_AUTH=true and restart. The switch was built to be exactly this cheap, and RequireAuthTest already pins the enforcing behaviour.

Do not flip it before C-3. With the committed signing key still in place an attacker forges a superadmin token and enforcement buys nothing. Order: rotate the JWT secret → flip enforcement → verify every page still works.

Then close the remaining gap: require-auth is authentication, not authorization. Once on, every caller is someone — but any authenticated practitioner can still call every admin endpoint. The role and urlPath model exists and is returned to the frontend, yet is enforced only in the UI. Server-side authorization is the follow-on work.

C-2

Date of birth is the only credential, for every account type

Evidence
  • model/auth/User.java — "dob is the credential by product decision"; stored as a plain LocalDate, compared directly.
  • DashboardAuthService · PortalAuthService — user.getDob().equals(dob). No hash, no salt, no KDF, because there is no password.
  • No rate limiting, lockout, throttling or CAPTCHA anywhere — greps for ratelimit, bucket4j, lockout, 429 return nothing.
  • No MFA, no credential rotation, no password-change endpoint, no server-side logout.
Impact — four compounding problems
  1. A date of birth is not a secret. It is a data field — shown in the dashboard, editable in the respondent form, exported in reports, typed into the bulk XLSX sheet. Every administrator who can see a profile is holding that person's password, and every uploaded spreadsheet is a cleartext credential file.
  2. The keyspace is tiny and unthrottled. A working-age adult's dob is one of roughly 11,000–18,000 dates. With no rate limiting that is minutes of scripted requests per account — and combined with C-1, the attacker doesn't even need the email list, since the reports endpoint hands it over.
  3. It applies to superadmins. The two seeded accounts in application.yml are admin@bodh / 2001-01-01 and superadmin@bodh.biz / 1990-01-01 — a working credential pair, in version control, for the highest-privilege role (see C-3).
  4. Tokens cannot be revoked. Stateless JWTs with a 12-hour expiry, no denylist, no server-side logout. A compromised token is valid for its full lifetime regardless of what you do to the account.
Fix — a product decision, so the answer differs by audience

Dashboard accounts (do first, not controversial): real passwords with BCrypt or Argon2id, a length policy, forced rotation of the seeded superadmins, and TOTP MFA for any account with the superAdmin flag. RBI's IS Audit expectations for privileged access make MFA effectively mandatory the moment a bank or NBFC becomes a client.

Respondent portal (where the friction argument is real): dob-only login exists because respondents are one-time users who will not manage a password — a legitimate position. Preserve it without the vulnerability: keep dob as a convenience factor, paired with something the respondent possesses — a one-time link or OTP to the email/phone already on file, or a per-attempt access code issued with the assignment.

Immediately, regardless: rate-limit /api/auth/login and /api/portal/login. A small change that removes most of the practical risk while the larger decision is made.

C-3

Working credentials and signing keys are committed to git

git ls-files also confirms .env, bodhassess-app/.env, .env.production, .env.staging, .env.local and deploy.production.env are tracked despite .gitignore listing several — gitignore does not affect files already added. Their contents today are non-secret, but the pattern is one commit from leaking one. deploy.production.env also publishes the production host as root@168.144.118.157.

Impact

If JWT_SECRET is not overridden in production, anyone with repository access — 10 contributors are in the log, plus anyone it has ever been shared with — can forge a valid superadmin JWT. That makes C-1's fix ineffective on its own. The MySQL root password is a full-database credential.

Fix

Rotate the JWT secret to a fresh 32+ byte random value supplied only via secrets.env (this invalidates all live sessions — desirable). Rotate the MySQL root and application passwords. Change the seeded superadmin dobs in the database — the seeder only ever adds, so editing the YAML changes nothing for an existing account.

Remove defaults from source, and make the app fail to start when JWT_SECRET is unset in the production profile: a missing secret should be a loud boot failure, never a silent fallback to a public value. git rm --cached the tracked env files. Rewriting history is optional and disruptive — rotation is what removes the risk; treat the historical values as permanently public.

High — 4 findings
H-1

The entire database is backed up unencrypted to a shared bucket in Singapore

Evidence — ops/README.md · bodh-db-backup.sh
  • Nightly full mysqldump → gzip → s3://storage-c9/bodhpsychometric/ on DigitalOcean Spaces, region sgp1 (Singapore).
  • storage-c9 is documented as shared with another product (~3.4 GB of unrelated reports and logos).
  • The dump is gzipped only — not encrypted. Compression is not confidentiality.
  • Retention 10 days. Spaces credentials are correctly kept in a root-only 0600 file.
Impact — three distinct problems
  1. Data residency. Every respondent's name, email, dob (which is also their password), phone, gender and complete response history leaves India nightly. A cross-border transfer under DPDP, and a hard blocker for any RBI- or SEBI-regulated client — the flow-down expectation of India-resident storage is where a vendor assessment stops.
  2. Tenant segregation. A shared bucket means one credential compromise, or one over-broad IAM policy, exposes your data alongside another product's. ISO 27001 A.5.14/A.8.12 and SOC 2 CC6.7 ask you to demonstrate segregation you cannot currently demonstrate. The prune logic is carefully confined to your prefix — good discipline, but confinement of writes is not isolation of reads.
  3. No encryption at rest. Anyone who obtains one object obtains the whole database in plaintext.
Fix — in priority order

Encrypt the dump before upload (AES-256 via gpg or age, key held off the droplet, restore path tested) → move to an India region (blr1, or S3 ap-south-1) → dedicated bucket with a scoped-down key → document the retention decision, since 10 days is short for a compliance narrative and auditors will ask what it is based on.

Schedule and record a restore test. The script verifies dump integrity — size and the Dump completed trailer — which is genuinely good practice. But nothing records that a restore has ever been performed, so your RTO and RPO are unproven assertions.

H-2

No encryption at rest anywhere in the stack

Evidence
  • MySQL 8 on a plain Docker volume. No TDE, no encrypted tablespaces, no keyring plugin in compose.
  • JDBC URL sets useSSL=false in both profiles — application-to-database traffic is cleartext on the bridge network.
  • Redis persists to a volume holding partial answers (1-day TTL) and staged submissions (7-day TTL) — real response data, unencrypted. requirepass is correctly set and publishing is loopback-only.
  • Application-level encryption: greps for Cipher, AES, encrypt return nothing.
Impact

Any filesystem-level access — a stolen volume snapshot, a droplet compromise, a mis-scoped API token, a decommissioned disk — yields everything in plaintext. Psychometric response data is behaviourally revealing and, depending on the instrument, may attract heightened treatment under DPDP and would be special-category data under GDPR Art. 9.

Fix

Enable InnoDB tablespace encryption, or move to a managed database with encryption on by default. Turn on TLS for the JDBC connection — useSSL=false is a dev convenience that shipped to production. Consider column-level encryption for dob specifically, since it doubles as a credential.

H-3

Session tokens in localStorage, one unguarded HTML sink, no CSP

Evidence
  • Both frontends store the bearer token in localStorage — readable by any JavaScript on the origin.
  • model/RichTextHtml.java is a strong control: a strict tag allowlist that rejects rather than sanitizes, correctly reasoned in its own comments, covering terms, questionnaire and section instructions.
  • The gap is elsewhere — chat-sheet.tsx:210,248 renders message.text through dangerouslySetInnerHTML with no allowlist and no sanitizer. No DOMPurify dependency exists in either project.
  • nginx sets no Content-Security-Policy, so nothing contains a slip. No token revocation (C-2), so a stolen token is good for up to 12 hours.
Fix

Add DOMPurify and sanitize every dangerouslySetInnerHTML sink not already covered by RichTextHtml; ship a CSP from nginx; then move tokens to HttpOnly; Secure; SameSite=Strict cookies with CSRF protection. CSP plus sanitization removes most of the practical risk first.

H-4

No security headers, no TLS policy, no edge rate limiting; permissive CORS

Evidence — nginx/conf.d/default.conf
  • Confirmed absent: Strict-Transport-Security, X-Content-Type-Options, X-Frame-Options, Content-Security-Policy, Referrer-Policy, Permissions-Policy. A grep for add_header returns nothing.
  • ssl_protocols and ssl_ciphers are unset — whatever the nginx image defaults to is your TLS policy, undocumented and unpinned. An auditor will ask you to state it; today you cannot.
  • No limit_req — no rate limiting at the edge, which is where C-2's brute-force protection most cheaply belongs.
  • Only api.bodh.biz is served here. The portal.bodh.biz block is commented out and there is no admin.bodh.biz block at all — so where those two are served, and under what policy, is not evidenced in this repository.
  • https://*.bodh.biz via allowedOriginPatterns with allowCredentials(true) — every subdomain is a trusted origin, including any ever mis-provisioned, parked or taken over.
Fix

Add the header set and an explicit modern TLS policy (TLS 1.2+, named cipher suite). Add limit_req zones for the two login endpoints. Replace the CORS wildcard with the explicit list of origins you actually operate, and document the serving path for the dashboard and portal.

Medium — 5 findings
M-1

No CI, no dependency scanning, no SAST

.github/ contains only Claude modernization hooks — no workflows. Greps for trivy, snyk, dependency-check, codeql, semgrep, npm audit return nothing anywhere in the repo.

Current dependency posture is actually good — Spring Boot 4.1.0, Java 25, jjwt 0.12.6 are all current, with no obvious vulnerable component. The finding is not "you have a vulnerable dependency"; it is that nothing would tell you when you do. ISO 27001 A.8.8 and SOC 2 CC7.1 both require a defined, evidenced process.

Fix

A GitHub Actions workflow running mvn test, npm audit --audit-level=high, Trivy or OWASP Dependency-Check, and secret scanning (gitleaks) on every PR. Enable Dependabot. Half a day of work that produces continuous audit evidence.

M-2

Audit trail is well-built but not audit-grade

ActivityLog is one of the better pieces of this codebase and deserves credit: every request recorded including reads, actor captured as a snapshot with no FK so the row outlives the account, deliberate exclusion of bodies, tokens, dob, answers and demographic values, an async write that drops rather than blocks, and a 365-day retention default.

Four gaps stand between it and audit-grade:

  1. No integrity protection. Rows sit in the same MySQL an administrator can reach. Nothing is append-only, hash-chained, or shipped to write-once storage. An auditor asks: what stops a privileged user editing the log that records what they did?
  2. The auditors are not audited. The filter skips /api/activity by design — reasonable to avoid recursion, but "who read the audit trail" is unanswerable. That is precisely what SOC 2 CC7.2 and RBI IS Audit look for.
  3. Attribution is empty while C-1 stands. With require-auth off, most rows record anonymous. The trail cannot attribute anything, which is the whole point of a trail.
  4. No alerting. Rows are written and viewable; nothing watches them. No SIEM, no anomaly detection, no on-call path.
Fix

Ship activity rows to an append-only external store or hash-chain them in place; log audit-viewer reads to a separate stream; alert on the signals that matter — bulk report reads, failed logins, privilege changes.

M-3

Data retention and erasure are not implemented

  • Erasure. DELETE /api/respondents/delete/{id} returns 409 whenever the respondent has any attempt. Correct as a data-integrity choice — but it means the people whose data is most sensitive have no erasure path at all. DPDP §12 and GDPR Art. 17 both require one.
  • Retention. No schedule for AssessmentAnswer, DemographicResponse or RespondentUser. DPDP §8(7) requires erasure once the purpose is served. ActivityLog is the only entity with a retention policy — apply the same thinking to personal data.
  • Consent withdrawal has no effect. The transitions are handled correctly — first grant stamps consentedAt, revoke clears it — but revoking flips a boolean and deletes nothing. Under DPDP, withdrawal must stop processing and trigger erasure absent another lawful basis.
  • No data-subject request process. No endpoint, runbook or SLA for access, correction, erasure or grievance. DPDP requires a Consent Notice, a published Grievance Officer, and a defined response mechanism.

Credit where due: consent capture itself is real and better than most — is_consented + consented_at, plus AssessmentTerms showing versioned terms before the first question with a sensible default body. The foundation is there; the lifecycle around it is missing.

Fix

Define retention periods per data class and implement a purge job. Implement anonymization — sever RespondentUser from User, retain de-identified answers for statistical validity — as the erasure path that survives the FK constraint, and make consent withdrawal trigger it. Publish the Consent Notice and Grievance Officer.

M-4

No documented ISMS

The single largest gap for ISO 27001, ISO 27007 and SOC 2 — and not a code problem. Certification audits assess documented, operating, evidenced processes, not source code. Currently absent:

  • Information security policy set; risk assessment and treatment plan; Statement of Applicability
  • Asset inventory and data classification; Record of Processing Activities
  • Access control policy and periodic access reviews — 10 contributors have repository access; who holds droplet, database and Spaces access is recorded nowhere
  • Supplier register and assessments — DigitalOcean (compute, Spaces), Let's Encrypt, any subprocessors
  • Incident response and breach notification — DPDP requires notifying both the Data Protection Board and every affected Data Principal, on a clock. No plan, no severity model, no comms template, no on-call rotation.
  • Business continuity and disaster recovery with a tested restore (see H-1)
  • Secure SDLC, change management, onboarding/offboarding, security awareness training records
Fix

Three to six months of deliberate work. Start with asset inventory, Record of Processing Activities, risk register and incident response plan — those four unlock most of the rest, and are what a DPDP regulator would ask for first.

M-5

Single-host production with root SSH deployment

One droplet running MySQL, Redis, the API and nginx, deployed to as root. No HA, no failover, no documented patch cadence, no host hardening baseline, no log shipping, no IDS. Availability is a SOC 2 criterion and BCP an ISO 27001 requirement; both are currently unevidenced.

Credit: the port-publishing policy in docker-compose.yml is a genuinely good control — everything bound to 127.0.0.1 except nginx, with DOCKER-USER DROP rules as a second layer, and a correct note that Docker writes iptables directly and bypasses ufw. That came from a real Shadowserver notice about exposed Redis and was handled properly. Keep it and document it — it is exactly the evidence an auditor wants.

Fix

Non-root deploy user with scoped sudo; SSH keys only with root login disabled; documented patching; a managed database (which also solves H-2's encryption and H-1's residency); and eventually a second host.

Low — 2 findings
L-1

Verbose error messages in production

spring.web.error.include-message: always in the production profile. Stack traces are correctly suppressed and ApiExceptionHandler is well-built, so exposure is small — but exception messages can leak internal structure. Consider on-param for production.

L-2

Employee-ID login can silently fail on collision

PortalAuthService.byEmployeeId returns a generic 401 when an employee ID + dob matches more than one person across organizations. The reasoning is documented and correct — rejecting beats guessing, and email login still works — but the affected user gets an unexplainable failure with no signal to support. Log the collision so it is diagnosable.

What is already working

Real controls that will earn credit in an audit. None should be lost during remediation.

Flyway + ddl-auto: validate

Disciplined, reviewable, non-repudiable schema change control. Directly satisfies change-management expectations (ISO A.8.32, SOC 2 CC8.1).

ActivityLog

Every request, actor as an FK-less snapshot, no sensitive payloads, async and non-blocking, bounded queue that drops rather than OOMs, retention policy. A strong foundation.

RichTextHtml

A reject-don't-sanitize allowlist with the reasoning documented in the code. The right call, correctly argued.

Container port policy

Loopback-only binding plus DOCKER-USER DROP rules, with the ufw-bypass trap correctly identified. Incident-driven and well handled.

Backup integrity discipline

Dump verified before upload, upload confirmed before prune — so failures degrade to stale backups, never to no backups. Better reasoning than most production systems have.

Credential-oblivious responses

Identical messages for unknown identifier and wrong dob; workbook strangers get 404 rather than 403. Correct enumeration hygiene.

DataStudioAccess

A proper four-level authorization model with a single enforcement point. This is the pattern the rest of the API needs.

RequireAuthTest

Enforcing mode is already pinned by tests, so flipping C-1's switch is a known quantity rather than an experiment on staging.

Validation single-sourcing

E.164 phone rules and @BirthDate bounds live in one place each, with the cross-field constraint handled properly.

Remediation roadmap

Four phases. Within the first, the order matters — rotating the signing key must precede enabling enforcement.

This week
  1. Verify whether REQUIRE_AUTH and JWT_SECRET are overridden in production.
  2. Rotate the JWT secret, MySQL root and app passwords, and the seeded superadmin credentials in the database.
  3. Enable REQUIRE_AUTH=true and regression-test both frontends end to end.
  4. Rate-limit both login endpoints — nginx limit_req is the fastest path.
  5. Encrypt the nightly backup before upload, and test a restore.
  6. Add security headers and a TLS policy to nginx; replace the *.bodh.biz CORS wildcard.
  7. Sanitize the chat-sheet.tsx HTML sink.

Steps 2 and 3 are a pair. Enforcement without rotation is defeated by a forged superadmin token.

30 days

Server-side authorization on every admin endpoint, extending the DataStudioAccess pattern · real passwords and MFA for dashboard accounts · CI with dependency, secret and static scanning · backups moved to an India region and a dedicated bucket · MySQL encryption at rest and TLS on the JDBC connection · non-root deploy user.

90 days

Decide and implement the portal's second authentication factor · retention schedule and purge job · anonymization-based erasure path · Consent Notice, Grievance Officer and DSR process · incident response and breach notification runbook · asset inventory and Record of Processing Activities · risk register.

6 months

ISMS documentation set and internal audit · access reviews and supplier assessments · BCP/DR with tested restore · security awareness training · then engage a certification body for ISO 27001 Stage 1, and a CPA firm for SOC 2 Type I with a Type II observation window to follow.
